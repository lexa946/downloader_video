# Запуск сервиса

Серверу нужны Docker Compose, доступ к YouTube, Instagram, VK и отдельное S3-совместимое хранилище. В S3 создайте бакет для превью и разрешите публичное чтение объектов из него. Для S3 нужен действующий TLS-сертификат. Внешний HTTPS-прокси может передавать запросы на `127.0.0.1:8084` и не должен буферизовать ответ `/api/get-video/`, поскольку через него передаются большие файлы.

1. Скопируйте `.env.production.example` в `.env.production` и заполните адреса S3, имя бакета и ключи. `S3_PUBLIC_URL` должен открываться браузером посетителя по HTTPS. Файл `.env.production` исключён из Git. Выдайте ему доступ только администратору сервера.
2. Проверьте, что публичное имя сайта соответствует canonical URL в шаблонах `app/frontend` и `sitemap.xml`. Сейчас там указан `https://downloader.pozharsite.ru`.
3. Настройте DNS и HTTPS-прокси. Для передачи cookie сайт должен открываться через HTTPS. Прокси должен передавать заголовки `Host` и `X-Forwarded-Proto`.
4. Запустите стек из корня проекта.

```sh
docker compose --env-file .env.production -f docker-compose.yaml config --quiet
docker compose --env-file .env.production -f docker-compose.yaml up -d --build --wait
docker compose --env-file .env.production -f docker-compose.yaml ps
```

Если при запуске появляется `ValidationError` с отсутствующими `FFMPEG_PATH`, `S3_*` и `REDIS_*`, контейнер не получил файл настроек. Запускайте команды из каталога с `docker-compose.yaml` и `.env.production`. Проверьте наличие всех ключей из `.env.production.example`. `--env-file` передаёт переменные в Compose, а строка `env_file` в `docker-compose.yaml` передаёт их контейнерам. После исправления пересоздайте веб-сервис и воркер командой `docker compose --env-file .env.production -f docker-compose.yaml up -d --build --force-recreate --wait`. Не публикуйте вывод `docker compose config` без `--quiet`, поскольку в нём видны секреты.

Redis доступен только сервисам Compose. По умолчанию сайт публикуется на `0.0.0.0:8084`, то есть доступен по IP машины и порту 8084, если этот порт открыт в брандмауэре и сети. `WEB_BIND_HOST` и `WEB_PORT` меняют адрес и порт публикации. Если сайт должен быть доступен только локальному HTTPS-прокси, установите `WEB_BIND_HOST=127.0.0.1`. Контейнеры веб-сервиса и воркера используют общий том `downloads`. Данные Redis находятся в томе `redis_data`. Не удаляйте эти тома при обновлении.

Корневой `main.py` используется для запуска Python вне Docker и слушает `127.0.0.1:8000`. Docker запускает Uvicorn командой из `Dockerfile` на порту 80 внутри контейнера. Запись Compose `0.0.0.0:8084:80` связывает порт 8084 машины с портом 80 контейнера. Для проверки с другого устройства используйте `http://IP_МАШИНЫ:8084/`. Если страница открывается на самой машине, но не открывается с другого устройства, проверьте публикацию порта командой `docker compose --env-file .env.production -f docker-compose.yaml ps`, правила брандмауэра ОС и сетевого провайдера, а также правильность IP. После изменения порта пересоздайте контейнер через `up -d --force-recreate --wait`.

При обращении напрямую по HTTP установите `COOKIE_SECURE=false`, иначе браузер не сохранит cookie согласия и работа сервиса останется заблокированной. Для публичного запуска включите HTTPS и верните `COOKIE_SECURE=true`.

Если Nginx стоит перед приложением, в логах контейнера без доверия к proxy-заголовкам виден IP соединения от Nginx. Это может быть адрес шлюза Docker, например `192.168.16.1`. Убедитесь, что Nginx передаёт заголовки ниже в том `location`, который проксирует приложение:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Задайте в `.env.production` параметр `TRUSTED_PROXY_IPS` равным адресу **источника соединения Nginx**, который виден в логах контейнера, затем пересоздайте веб-контейнер. Доверять proxy-заголовкам со всех адресов при открытом прямом доступе на `8084` небезопасно: клиент сможет подставить произвольный IP. Если адрес Nginx меняется, используйте стабильный адрес или ограниченную подсеть Docker. Для публичного сайта предпочтительно ограничить прямой доступ к `8084` и принимать запросы через HTTPS-прокси.

После запуска проверьте главную страницу через публичный HTTPS-адрес. Откажитесь от cookie и убедитесь, что API скачивания возвращает `403`. Затем примите cookie, загрузите короткое видео с каждой площадки, дождитесь статуса готовности и сохраните файл. Проверьте декодирование файла плеером. Рабочее состояние и ошибки видны в логах.

```sh
docker compose --env-file .env.production -f docker-compose.yaml logs --tail=100 downloader_video worker redis
```

Для обновления сохраните копию `.env.production` и томов `downloads`, `redis_data`, затем повторите `up -d --build --wait`. Готовые файлы удаляются после передачи пользователю. Файлы, которые не забрали, удаляет ежедневная задача после `CLEANUP_RETENTION_HOURS` часов. Оцените доступный диск с учётом числа одновременных загрузок и размера больших видео. Настройте мониторинг свободного места, здоровья контейнеров и времени загрузки.

Установите `WORKER_MAX_JOBS` исходя из пропускной способности сервера и канала. Каждая задача YouTube может открывать до четырёх соединений для видео. При нескольких воркерах все они должны разделять Redis и том `downloads`. Перед увеличением числа воркеров проверьте диск, сеть и время получения файла на ожидаемой нагрузке.

## Mihomo для YouTube и Instagram

В `.env.production` задайте `MEDIA_PROXY_URL=http://192.168.1.138:7490`. Это HTTP-порт Mihomo на вашем сервере. Порт `7892` тоже подходит, если настроен как mixed-port. Порт SOCKS-only без HTTP-интерфейса здесь не подходит. Compose передаёт адрес прокси веб-сервису и воркеру. Mihomo должен принимать соединения с Docker-сети. Если слушает только на `127.0.0.1`, контейнер к нему не подключится. Настройте в Mihomo `allow-lan` и `bind-address` для адреса сервера и ограничьте доступ к порту прокси средствами брандмауэра.

При старте веб-приложение и worker отдельно проверяют TCP-соединение с Mihomo и пишут в Docker-логи `Mihomo HTTP proxy is reachable` или `Mihomo HTTP proxy is unreachable`. Проверка подтверждает доступность порта из контейнера. YouTube и Instagram используют прокси при чтении страницы, поиске, получении форматов, превью и скачивании медиа. VK подключается напрямую. При пустом `MEDIA_PROXY_URL` площадки используют прямое соединение. После изменения `.env.production` пересоздайте оба контейнера приложения.

```sh
docker compose --env-file .env.production -f docker-compose.yaml up -d --build --force-recreate --wait
docker compose --env-file .env.production -f docker-compose.yaml logs --tail=30 downloader_video worker
```

Вторая команда проверяет TCP-доступность порта Mihomo из контейнера. Затем проверьте получение форматов и скачивание по одной ссылке с YouTube, Instagram и VK. Если порт Mihomo недоступен, проверьте его адрес прослушивания и правила брандмауэра хоста. Не используйте `127.0.0.1` в `MEDIA_PROXY_URL`, когда Mihomo запущен вне контейнера.
